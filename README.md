# Gold COT Lab · 黄金持仓分析实验室

一个本地跑的黄金期货持仓研究工具。

它**不预测金价**，也不给你买卖信号。它只做一件事：把美国 CFTC 每周公布的持仓报告整理干净，然后回答四个具体问题。

1. 管理基金现在积累了多少净多头？是在继续加仓，还是开始撤退？
2. 当前持仓在过去十几年里处于什么位置？
3. 黄金涨跌是得到基金持仓支持，还是在背离？
4. 目前的数据支持哪些判断，哪些判断其实还缺证据？

技术栈刻意选得笨重而可靠：**React + ECharts 前端 / FastAPI + Pandas 后端 / SQLite 存储 / 只用免费的官方数据**。第一版没有 AI、没有付费数据库、没有黑箱。

## 怎么打开

### 最简单的方式：双击启动文件

- **Windows：双击 `启动.bat`**
- **苹果电脑（macOS）：双击 `启动.command`**

两个文件干的是同一件事，就一下，别的什么都不用管：

1. 双击项目根目录里的启动文件（Windows 是 `启动.bat`，Mac 是 `启动.command`）
2. 会弹出一个窗口，自动显示四行进度（检查环境 → 检查持仓数据 → 检查黄金价格 → 检查指标与界面）
3. 浏览器**自动打开**，界面就出来了
4. 用完了回到那个窗口，按 `Ctrl+C` 或者直接关掉窗口

第一次运行会自动装依赖、导入历史数据、抓黄金价格、算指标，慢一点是正常的。之后再打开就很快了，因为数据都存着。

Windows 上，`启动.bat` 会先把控制台切到 UTF-8（`chcp 65001`），Python 侧也把输出重定向成 UTF-8 —— 这样不管你的 Windows 是中文版还是英文版、控制台默认码页是什么，中文进度都不会变成乱码或直接崩掉。

**前提只有一个：电脑上装了 Python 3.10 或更新版本。**

- Windows：[下载地址](https://www.python.org/downloads/)，安装时记得勾选 **Add python.exe to PATH**。
- macOS：[下载地址](https://www.python.org/downloads/macos/)。系统自带的 Python 往往版本太老，建议装官方版。

没装的话，双击启动文件会弹一段中文提示告诉你怎么办，不会闪一下就没了。

#### 苹果电脑的两个小提醒（都只需做一次）

1. **可能要给它一次执行权限。** macOS 要求这种双击脚本带「可执行」标记，而这个标记在网络传输时（比如 Windows 打包的压缩包）经常会丢。如果双击后提示权限不足，打开「终端」，输入 `chmod +x `（注意后面有一个空格），把 `启动.command` 拖进终端窗口，回车即可。
2. **可能被系统拦一下。** 如果提示「来自身份不明的开发者」，在文件上**右键 → 打开**，再点一次「打开」。之后就直接双击了。

另外，Mac 上第一次运行会在项目文件夹里自动建一个 `.venv` 目录（一个独立的 Python 环境）。这样装依赖不用管理员权限，也不会动你系统上的 Python —— 这是 macOS / Linux 上的通行做法，删掉它无损，下次启动会重建。

想改界面代码的人还需要 Node.js；只想用的人完全不用管它。

## 数据从哪来，以及它们各自的坑

### COT 持仓：唯一的主数据源

CFTC（美国商品期货交易委员会）官方免费发布，用的是 **Disaggregated Futures Only** 报告（数据集 `72hh-3qpy`），历史自 2009 年 9 月起。

第一版不导 Legacy 报告。原因很实在：**Disaggregated 里的 Managed Money 和 Legacy 里的 Non-Commercial 不是同一个东西**，把它们接成一条连续的 Managed Money 序列是错的。两种口径将来会各自入库、各自算指标。数据库的唯一键 `(report_type, market_code, report_date)` 已经为此留好位置，`cot_weekly` 里的 `noncomm_*` / `comm_*` 列也是空的，就等 Legacy 进来。

当前这份历史来自一份官方导出 CSV（1233 行 × 194 列，三个黄金相关市场：COMEX Gold 1061 期、Micro Gold 166 期、Coinbase 1oz Gold 6 期）。**194 列一列不丢**，全部原样存在 `cot_raw.raw_json` 里。

### 黄金价格：辅助数据，可以完全没有

价格是可选的。价格适配器按「降级优先」写，从国内能直连的源开始试：

1. **新浪财经** 取 COMEX 黄金连续合约 `GC` —— 国内直连、响应快，实测一次能拿到 2016 年至今约 2590 个交易日（这也是默认第一个试的源）
2. `yfinance` 取 `GC=F`（COMEX 连续近月期货，和 COT 报告口径一致）
3. `stooq` 取 `xauusd`（**现货金，不是期货**，入库时 `source_symbol='xauusd'` 并写进 `issues` 明确标注）
4. 你自己丢到 `data/raw/prices/manual_GC_F.csv` 的文件

新浪那个接口返回的是 JSONP，而且**必须带 `Referer: https://finance.sina.com.cn`** 才会给你正常数据；它的成交量字段恒为 0，所以干脆不存。

全都拿不到会怎样？**什么都不影响**。价格更新失败只会写一条 `status='failed'` 的日志（`error_json` 里逐个写明每个源失败的原因），然后正常返回。所有依赖价格的指标老老实实留成 `invalid_reason='no_price'` 的无效值 —— **不是 0，也不是假装算出来的数**。前端显示「价格数据不可用」，不报错。

这不是偷懒。手工验证过：本机环境下 yfinance 抛 `YFRateLimitError`、stooq 返回 JS 挑战页、东方财富 `push2his` 直接断连、CFTC API 返回 403；只有新浪财经稳定可用。把地基绑在随时会断的外部网络上，是最不该做的设计。

价格已经在总览页叠进走势图了：一条线是基金净持仓，另一条是 COMEX 黄金期货收盘价（右轴，美元/盎司）。想让图表好看点，去「数据管理」页点一下「获取黄金价格并重算指标」就行，不用敲命令。

想试价格链路可以自己造一份 CSV 丢进 `data/raw/prices/`：

```bash
python -m backend.data.price_client --source manual_csv --dry-run   # 只看不写
python -m backend.data.price_client                                  # 真写，幂等
```

顺手提醒：`GC=F` 是连续合约。换月那天价格可能凭空跳一下 —— **那是合约换月，不是行情**。适配器会把单日涨跌超过 8% 的位置列成 `jump_candidates` 报给你看，但绝不替你抹平。免费行情用来做研究原型可以，**不能当成可交易的价格序列**，也不能假设它有交易所级的完整性和稳定性。

## 时间口径：这个工具最容易搞错、也最较真的地方

CFTC 在**周五**发布报告，报告里统计的是**前一个周二**的持仓。所以有两个日期，界面上分开显示，绝不混用：

- **数据截至日**（`report_date`）：那周的周二。这是持仓真正发生的时间。
- **实际发布日**（`published_at`）：周五 15:30 ET。这是你**最早能看到**它的时间。

所有历史分析都必须按「当时看得见什么」来，否则就是在用未来信息骗自己。接口提供三种口径：

| `pit_mode` | 含义 | 什么时候用 |
|---|---|---|
| `published_at` | 默认。按推导的发布时刻过滤 | 正常回看 |
| `conservative` | 报告日 + 7 天 | 保守回测，宁可少看几期 |
| `report_date` | 直接用报告日 | **有前视偏差**，界面会标红警告 |

一个诚实的局限：`published_at` 是**按规则推导**出来的（`published_at_source='derived'`），不是从官方发布记录里抓的真实时间戳。它只是真实可见时间的**下界** —— 反映不了真实的延误（2018–19 和 2025 年政府停摆会导致几周不发布然后集中补发），也反映不了官方事后修正。表里留了 `published_at_source` 字段，将来可以换成真实发布时间。

顺带一提，推导逻辑不是简单地「加 3 天」：它会跳过联邦假日（`config.py` 里程序化生成，含 Juneteenth 和「周六假日提前到周五补休」这类规则），并且正确处理夏令时 —— 夏天是 19:30 UTC，冬天是 20:30 UTC。

## 指标怎么算的

六类，全部只用**向后滚动窗口**（当期 + 之前），绝不会把未来数据混进历史值。无效结果写成 `value_num = NULL` + `is_valid = 0` + `invalid_reason`，**从不写 0，也不抛异常中断整批**。

**A. 净持仓与周度变化** —— `Net = Long − Short`，变化量**拆开算** `ΔLong` 和 `ΔShort`。

拆开是有意义的：净多头变多，可能是新开多头，也可能是空头回补 —— 这是两种完全不同的行为，合成一个数字就看不出来了。

**B. 净持仓占比** —— `Net / OI × 100%`。看基金的净方向性仓位相对市场规模有多大。它补充净持仓绝对手数，但替代不了。

**C. 历史分位** —— 当前净持仓在**过去 3 年 / 5 年**有效样本里的百分位。≥90% 历史相对高位，≤10% 历史相对低位。

注意：这是滚动窗口分位，**不是全历史分位**。这是正确性的要求，代价是数值更极端、更容易触发阈值。所以界面永远显示当前用的窗口。

**D. COT Index** —— `100 × (Net − min) / (max − min)`，窗口 26 / 52 / 156 周。

窗口内最大值等于最小值时，结果是**无效值**，不是除以零，也不是悄悄传下去的 NaN。

**E. 价格趋势与背离** —— 1/4/12 周收益率、4/12 周趋势、净持仓连续同向周数，以及四象限背离：

| 价格 | 净持仓 | 状态 |
|---|---|---|
| 上涨 | 增加 | 趋势与仓位一致 |
| 上涨 | 下降 | 价格与仓位背离 |
| 下跌 | 下降 | 趋势与仓位一致 |
| 下跌 | 增加 | 价格与仓位背离 |

**背离只说明「值得再多看一眼」，不意味着行情必然反转。**

价格和 COT 对齐时，取的是**发布日当天或之前**的最后一个收盘价。绝不能取报告日当天的收盘价 —— 那是未来信息。

**F. 极端仓位预警** —— 分位 >90% 或 <10% 时标记「高位/低位拥挤观察」，再结合价格趋势和连续增减仓生成解释文字。

所有阈值（`alert_high_pct`、`alert_low_pct`、窗口长度、`min_coverage`）都是可配置参数，存在 `params_json` / `params_hash` 里。

**阈值改动不算换公式。** 所以 `params_hash` 和 `calculation_version` 是两回事：调阈值只换 hash，改公式才换 version。`cot_indicators` 表按 version 分区，改完公式重算，旧结果还能拿来对比。

## 数据管理：为什么值得单独讲

这一页本身就是操作台，不用敲命令：**第一步**选一个 CFTC 导出的 CSV 文件（浏览器里直接选，上传后服务端会先把它原样存进 `data/raw/cftc/` 再解析，和手工拷进去的效果一模一样）；**第二步**点一下「获取黄金价格并重算指标」，价格拉回来顺手把依赖价格的指标一起重算好。每次操作的结果都写进台账，状态是中文句子。

**幂等。** 同一份数据导两次，最终记录数、每个字段、每个指标都不变，第二次 `rows_inserted=0`。已实测：1233 → 1233。

**原始与计算分离。** `data/raw/` 存原封不动的原始文件，数据库存清洗后的结构化数据，分析代码只读原始文件不写。将来发现某个指标算错了，重算就行，不用重新下载全部历史。

**修订默认「挡住」。** 万一上游某个关键字段变了，默认策略是 `log_and_hold`：**不覆盖旧值**，批次标成 `partial`，把变化记下来等人工确认。宁可挡住一次合法的官方修正，也不能让一次意外的数据变更悄悄污染数据库。要放行就显式加 `--accept-revisions`。

五张表：

| 表 | 干什么 |
|---|---|
| `cot_raw` | 原始层。官方 194 列原样存进 `raw_json`，加提升出来的键列 |
| `cot_weekly` | 标准化层。统一字段名和类型，`UNIQUE (report_type, market_code, report_date)` |
| `cot_indicators` | 指标结果。长表存储，含 `calculation_version` 和 `params_hash` |
| `price_daily` | 黄金价格，`UNIQUE (symbol, trade_date)` |
| `ingestion_log` | 每次更新的台账：来源、sha256、行数、校验报告、错误原因 |

导入时跑 R1–R15 共 15 条校验。其中一条比较反直觉：**不能要求「所有多头之和 = 所有空头之和」** —— 报告里含价差持仓和不同分类口径，这个等式本来就不成立。另外 `Change_in_*` 和 `Pct_of_OI_*` 这两组列都可以从持仓列精确重算，所以只留在 `raw_json` 里，不进标准化层（重复存储只会让「哪个才是对的」变得含糊）。

还有个坑值得记下来：**官方列名本身有笔误** —— `Swap_Positions_Long_All` 是单下划线，`Swap__Positions_Short_All` 是双下划线。所以内部字段名不沿用官方名，而是一列一列显式映射。

以及：**绝不能按 `Report_Date_as_YYYY_MM_DD` 字符串排序**。月份是英文缩写，字典序和时间序不一致，会让 `Change_in_*` 的重算凭空出现 244 处假不符。改成解析后按日期排序，是 0 处。

## 项目结构

```
gold-cot-lab/
├── 启动.bat                    # Windows：双击这个，别的都不用管
├── 启动.command                # 苹果电脑：双击这个，作用完全一样
├── backend/
│   ├── main.py                 # FastAPI 入口：/api 先挂，静态文件后挂
│   ├── config.py               # 路径、指标默认值、联邦假日表
│   ├── db.py                   # DDL、连接、point-in-time 的唯一实现点
│   ├── api/{cot,price,admin}.py
│   ├── data/{normalize,cftc_import,price_client}.py
│   ├── analysis/indicators.py
│   └── tests/
├── frontend/                   # Vite + React + TS，运行时依赖只有 echarts
├── data/
│   ├── raw/{cftc,prices}/      # 原始文件，只读不改
│   └── gold_cot.sqlite
├── scripts/{launch,init_history,recompute_indicators}.py
└── requirements.txt
```

`scripts/launch.py` 是双击启动器背后干活的那个：查依赖、补数据、挑端口、开浏览器。它不参与任何计算，只负责把环境摆好 —— 所以上面那些命令行的用法完全不受影响。

`resolve_as_of()` 和 `pit_clause()` 刻意都放在 `db.py`：**「在某时刻能看见什么」这件事只能有一份实现**，否则迟早会有一个接口偷偷用上未来数据，而且极难发现。

## 自检

```bash
python -m pytest backend/tests -q     # 52 项
```

重点盯这几类：

- **幂等**：同文件导两次，行数、行哈希、指标全部不变
- **手算校验**：分位和 COT Index 的数值对得上手算结果
- **字符串排序回归**：确保没人再把日期当字符串排序
- **无前视**：追加后续 60 期数据后，前 200 期的指标值逐一不变
- **前视偏差边界**：`as_of=2021-12-29` 时，`published_at` 模式看到 12-21，`report_date` 模式看到 12-28
- **原始层保真**：`raw_json` 的键与源文件 194 个头完全相等

- **CFTC 增量 API 适配器**（`backend/data/cftc_client.py`）—— 本机 `publicreporting.cftc.gov` 返回 403，所以当前历史底库完全来自那份官方导出 CSV。写这个适配器的意义是「以后能自动拿到新一期」，不是「现在能用」。
- **Legacy Futures Only 口径** —— 可以把部分分析历史推到 1986 年，但口径不同，必须单独入库、单独算指标。
- **规则式市场状态识别与回测**（`analysis/regime.py`、`analysis/backtest.py`）—— 这是整个计划里最后一步，前面地基不牢就不该动它。
- **价格数据的换月调整与真实发布时刻** —— 新浪拿到的 `GC` 是连续合约，换月那天会报一个 `jump_candidates` 提示但**不替你抹平**；真实发布时刻目前仍是按规则推导。两者都需要更认真的处理才配上生产。
